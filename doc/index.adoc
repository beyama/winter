Winter is a small and fast dependency injection library for Kotlin Multiplatform: JVM, Android,
iOS, macOS, JavaScript and WebAssembly.

* Dependencies are declared in immutable *components* with a plain Kotlin DSL. No annotation
  processing, no code generation and instances are created by your own factory functions.
* Components nest: a *subcomponent* describes a part of the application with a shorter lifetime,
  e.g. a user session or an Android activity. Its *subgraphs* see everything from their parent
  graph but not the other way around.
* Components can be composed from parts of different modules or targets: include, merge, derive
  and override them.
* Optional modules for property injection, Android lifecycles and JUnit 4/5 tests.

NOTE: All code samples in this guide are compiled and run as tests of the project, see
link:https://github.com/beyama/winter[the repository].
The API documentation is available link:api/index.html[here].

== Installation

[source,kotlin,subs="attributes+"]
----
dependencies {
    // Core
    implementation("io.jentz.winter:winter:{winter-version}")
    // Property delegates for classes that can't use constructor injection
    implementation("io.jentz.winter:winter-delegate:{winter-version}")
    // AndroidX support (includes winter-delegate)
    implementation("io.jentz.winter:winter-androidx:{winter-version}")
    // JUnit 4 and JUnit 5 support
    testImplementation("io.jentz.winter:winter-junit4:{winter-version}")
    testImplementation("io.jentz.winter:winter-junit5:{winter-version}")
}
----

Snapshot versions (ending with `-SNAPSHOT`) are published to the Maven Central snapshot repository:

[source,kotlin]
----
repositories {
    maven("https://central.sonatype.com/repository/maven-snapshots/")
}
----

Winter requires Java 17 and Kotlin 1.9 or newer, the AndroidX module requires minSdk 24.
Kotlin Multiplatform projects add the core and delegate modules to their common source set, see
<<Multiplatform>>.

== Concepts

[cols="1,4",options="header"]
|===
| Term | Definition

| Component
| The immutable registry that describes how to create dependencies. It may contain subcomponents.

| Graph
| Created from a component. It creates and holds the instances and is used to retrieve them.
  A graph lives until it is closed.

| Subcomponent / Subgraph
| A component nested in another component, identified by a qualifier. A subgraph is created from a
  subcomponent and has the graph of the parent component as parent. It can access all dependencies of
  its ancestors, but not the other way around.

| Scope
| The lifetime of an instance in a graph, e.g. one instance per graph (singleton) or one per request
  (prototype).

| Type key
| Identifies a dependency by its type and an optional qualifier.
|===

`CyclicDependencyException` with the chain of dependencies in its message.

== Composing components

Components can be put together from parts, e.g. one per feature module, and each target of an
application can compose them differently.

=== Include

`include` copies all dependencies of a component. Subcomponents with the same qualifier are merged
by default, so several features can contribute to the same subcomponent.

[source,kotlin,indent=0]
----
include::{core}[tag=include]
----

The second argument of `include` controls how subcomponents are handled:

[cols="2,5",options="header"]
|===
| SubcomponentIncludeMode | Behaviour

| `Merge` (default)
| Subcomponents with the same qualifier are merged.

| `Replace`
| An existing subcomponent with the same qualifier is replaced.

| `DoNotIncludeIfAlreadyPresent`
| A subcomponent is only included if no subcomponent with the same qualifier exists.

| `DoNotInclude`
| Subcomponents are not included.
|===

Including a dependency that already exists throws an exception, unless it happens in an `override`
block.

== Circular dependencies

Two dependencies can't depend on each other through their constructors. One of them has to receive
the other one after it was created, in a post-construct callback. The callbacks are called after the
whole dependency request was resolved, so both instances exist at that point.

== Thread safety

Graphs can be used from multiple threads. Instances are created while holding the lock of the graph
they belong to. Already created singletons are returned without locking.

On the JVM the lock of a graph is its monitor, on Kotlin/Native a reentrant lock from kotlinx-atomicfu.
JavaScript and WebAssembly are single threaded and don't lock.

== Multiplatform

The core and delegate modules are Kotlin Multiplatform libraries with the targets JVM, iOS
(`iosArm64`, `iosSimulatorArm64`, `iosX64`), macOS (`macosArm64`), JavaScript (`js`) and
WebAssembly (`wasmJs`). The JVM target is also used on Android. The AndroidX and JUnit modules are
Android and JVM only.

[source,kotlin,subs="attributes+"]
----
kotlin {
    sourceSets {
        commonMain.dependencies {
            implementation("io.jentz.winter:winter:{winter-version}")
            implementation("io.jentz.winter:winter-delegate:{winter-version}")
        }
    }
}
----

Gradle selects the artifact for the platform (`winter-jvm`, `winter-iosarm64`, `winter-js` ...) from
the Gradle module metadata of `io.jentz.winter:winter`, JVM and Android projects keep using
`io.jentz.winter:winter`. Builds without Gradle module metadata, e.g. Maven, need to depend on
`winter-jvm` and `winter-delegate-jvm` directly.

JVM projects need Kotlin 1.9 or newer. Kotlin/Native, JavaScript and WebAssembly libraries can only
be read by the Kotlin version they were built with or newer, these projects need Kotlin 2.4 or newer.

There are a few differences between the platforms:

* Type keys are based on `KClass` and `KType`. On the JVM `List` and `MutableList` are the same class,
  on the other platforms they are different classes, so `erased<List<Pump>>()` and
  `erased<MutableList<Pump>>()` are different keys there. Erased keys of arrays don't distinguish
  the element type on JavaScript, WebAssembly and Kotlin/Native, use `generic()` keys for arrays.
* `qualifier<Type>()` uses the qualified class name. Kotlin/JS has no qualified class names, there
  the qualifier is the simple class name plus a number that is unique while the program runs.
  Don't compare these qualifiers with string qualifiers.
* Type keys and error messages use the qualified class names on the JVM (Java binary names),
  Kotlin/Native and WebAssembly and the simple class names on JavaScript.
